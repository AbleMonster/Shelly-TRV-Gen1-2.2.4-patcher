# OTA Server

This document describes the local OTA firmware server included with the
Shelly TRV Gen1 2.2.4 Firmware Patcher project.

The server is implemented in:

```text
ota_server.py
```

It is intended specifically for transferring the combined patched
Shelly TRV 2.2.4 firmware generated by:

```text
patch_firmware_v.1.0.py
```

to a Shelly TRV (SHTRV-01) on the local network.

It is not intended to be a general-purpose firmware or HTTP server.

---

## Purpose

The Shelly TRV can retrieve firmware through its OTA HTTP interface.

`ota_server.py` provides a small local HTTP/1.1 server that:

1. automatically locates the expected patched firmware in `target/`,
2. validates the patched firmware before serving it,
3. detects a suitable local IPv4 address,
4. selects an available HTTP port,
5. serves only the expected patched firmware,
6. supports HTTP Range requests,
7. displays firmware-transfer progress,
8. prints the firmware URL,
9. prints an OTA URL template for the Shelly TRV.

The server does **not** modify firmware.

Firmware modification is performed separately by:

```text
patch_firmware_v.1.0.py
```

The server also does **not** automatically initiate an OTA update on a device.

The user explicitly starts the OTA operation using the URL printed by the
server or an equivalent request.

---

## Requirements

The OTA server requires:

- Python 3
- the combined patched GBL generated by `patch_firmware_v.1.0.py`
- a computer connected to the same local network as the Shelly TRV
- network connectivity between the TRV and the computer

No third-party Python packages are required.

The server uses only the Python standard library.

The OTA server uses the same fixed `target` directory as the patcher.

Repository layout:

```text
Shelly_TRV_2.2.4_Patcher/

├── ota_server.py
├── README.md

│   └── .gitkeep
└── tests/
    └── README.md
```

After the original firmware has been supplied locally and the patcher has
successfully run, the local `target` directory typically contains:

```text
target/
├── .gitkeep
├── SHTRV-01_build_2.2.4.gbl
└── SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

The OTA server automatically uses:

```text
target/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

No firmware path or filename is supplied to `ota_server.py`.

Original and patched firmware files inside `target/` are local files and must
not be committed to the repository.

## Expected firmware

The OTA server intentionally accepts only the exact combined patched firmware
produced by the current patcher.

Expected patched GBL filename:

```text
SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

Expected patched GBL size:

```text
1,106,384 bytes
```

Expected patched GBL CRC32:

```text
0xBAEB8265
```

Expected patched GBL SHA-256:

```text
7adbb31d6b7faa8b9290d7b3436af45d42af9c3602a7195cafab774ded84ac61
```

If the file does not match the expected patched firmware, the server refuses
to serve it.

This prevents accidentally selecting an unrelated, modified, incomplete or
incorrectly generated firmware image.

## Starting the server

First generate the patched firmware:

```bash
python3 patch_firmware_v.1.0.py
```

The patcher writes the validated output automatically to:

```text
target/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

Then start the OTA server.

On systems where binding to TCP port 80 requires elevated privileges:

```bash
sudo python3 ota_server.py
```

No firmware argument is required.

The server determines its own script directory and automatically loads:

```text
target/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

Before opening the HTTP server, the program validates the firmware.

Validation includes:

- file existence
- file type
- file size
- SHA-256
- stored GBL CRC32
- calculated GBL CRC32
- expected patched CRC32

The server starts only if validation succeeds.

---

## Firmware validation

The OTA server performs its own firmware validation independently of the
patcher.

This provides a second validation boundary between firmware generation and
network transfer.

The expected values are:

```text
Filename:
SHTRV-01_2.2.4_beacon_mdns_patch.gbl

Size:
1,106,384 bytes

SHA-256:
7adbb31d6b7faa8b9290d7b3436af45d42af9c3602a7195cafab774ded84ac61

CRC32:
0xBAEB8265
```

The server compares the calculated file values with these expected reference
values.

If validation fails, the HTTP server is not started and the firmware is not
served.

Firmware validation should not be bypassed to serve an unknown image.

---

## Network detection

The server attempts to determine a suitable local IPv4 address automatically.

The detected address is used for the HTTP server and for the firmware URL
printed to the console.

Example:

```text
Local IPv4 : 192.168.178.232
```

The actual address depends on the local network.

The Shelly TRV must be able to reach this address.

Systems with multiple network adapters, VPN connections or unusual routing
configurations may require additional attention if the automatically detected
address is not reachable from the TRV.

---

## Port selection

The server checks the preferred HTTP ports in this order:

```text
80
8000
```

If port 80 can be used, it is preferred.

If port 80 cannot be used, the server attempts to use port 8000.

On Unix-like operating systems such as macOS or Linux, binding to port 80
normally requires elevated privileges.

For that reason the tested command is:

```bash
sudo python3 ota_server.py
```

Example using port 80:

```text
http://192.168.178.232/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

Example using port 8000:

```text
http://192.168.178.232:8000/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

The actual address and selected port are printed by the server.

## Firmware URL

The firmware is served under the fixed filename:

```text
SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

The corresponding HTTP path is:

```text
/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

After startup, the server prints the complete firmware URL.

Example:

```text
http://192.168.178.232/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

If port 8000 is selected:

```text
http://192.168.178.232:8000/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

The firmware URL can also be requested from another device on the same local
network to verify HTTP reachability.

A successful download confirms that the HTTP server can transfer the firmware
over the network.

It does not by itself test firmware installation on the Shelly TRV.

---

## Starting the Shelly OTA update

The Shelly TRV OTA endpoint accepts a firmware URL.

General form:

```text
http://<SHELLY-TRV-IP>/ota?url=http://<COMPUTER-IP>/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

If the server selected port 8000:

```text
http://<SHELLY-TRV-IP>/ota?url=http://<COMPUTER-IP>:8000/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

Example using `curl`:

```bash
curl "http://192.168.178.226/ota?url=http://192.168.178.232/SHTRV-01_2.2.4_beacon_mdns_patch.gbl"
```

Use the actual addresses for the target TRV and the computer running the OTA
server.

Keep `ota_server.py` running until the firmware transfer has completed.

Do not intentionally interrupt power to the TRV while the firmware update is
in progress.

---

## Expected OTA response

When the OTA request is accepted, the Shelly TRV can return a response similar
to:

```json
{
  "status": "updating",
  "has_update": true,
  "new_version": "20240619-130912/v2.2.4@ee290818",
  "old_version": "20220202-080736/v2.1.3@d255ad74"
}
```

The exact previous firmware version depends on the device being updated.

The patched firmware deliberately retains the original Shelly 2.2.4 firmware
version string.

Therefore:

```text
20240619-130912/v2.2.4@ee290818
```

does not by itself distinguish the patched firmware from unmodified 2.2.4.

## HTTP implementation

The OTA server uses:

```text
HTTP/1.1
```

It supports both normal and byte-range firmware requests.

A normal request without a `Range` header receives:

```text
HTTP/1.1 200 OK
```

A valid byte-range request receives:

```text
HTTP/1.1 206 Partial Content
```

The server advertises:

```text
Accept-Ranges: bytes
```

The tested server identifies itself as:

```text
ShellyTRVOTA/1.0
```

---

## HTTP 200 full-transfer test

A complete HTTP transfer has been tested against the current OTA server.

The request returned:

```text
HTTP/1.1 200 OK
Server: ShellyTRVOTA/1.0
Content-Length: 1106384
```

The complete firmware file was transferred:

```text
1,106,384 bytes
```

The server reported successful completion of the HTTP transfer.

This confirms that:

- the server was reachable,
- the expected firmware path was served,
- full-file transfer worked,
- the expected file length was transferred,
- progress reporting operated.

It does not by itself establish successful firmware installation on a TRV.

---

## Range request support

The OTA server supports HTTP byte-range requests.

Supported range forms include:

```text
Range: bytes=0-
Range: bytes=<start>-<end>
Range: bytes=<start>-
Range: bytes=-<length>
```

For valid range requests, the server returns:

```text
HTTP/1.1 206 Partial Content
```

together with an appropriate:

```text
Content-Range
```

response header.

Invalid or unsatisfiable ranges are rejected.

Multiple ranges in a single request are not supported.

---

## HTTP 206 Range test

Range support has been tested explicitly using:

```bash
curl -v \
  -H "Range: bytes=0-1023" \
  -o /dev/null \
  "http://192.168.178.232/SHTRV-01_2.2.4_beacon_mdns_patch.gbl"
```

The server returned:

```text
HTTP/1.1 206 Partial Content
Server: ShellyTRVOTA/1.0
Content-Range: bytes 0-1023/1106384
Content-Length: 1024
```

Exactly:

```text
1,024 bytes
```

were transferred.

This confirms correct operation of the tested Range request.

---

## Served paths

The OTA server is deliberately restrictive.

It serves only the expected firmware path:

```text
/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

It does not provide directory listings.

It does not expose the contents of:

```text
target/
```

as a general directory.

It does not expose arbitrary files from the computer.

Requests for unrelated paths are rejected.

---

## Transfer progress

During a firmware transfer, the server displays progress information in the
console.

The displayed information can include:

- requesting client
- requested byte range
- HTTP response status
- number of bytes requested
- number of bytes transferred
- transfer percentage
- progress bar
- current transfer rate
- transfer duration
- average transfer rate
- completion or interruption status

This makes it possible to observe whether the TRV is actively retrieving the
firmware.

For a Range request, the server can additionally show the position of the
transferred range within the complete firmware image.

---

## Meaning of transfer completion

A completed HTTP transfer means that the server successfully wrote the
requested firmware data to the HTTP connection.

It does **not** prove that:

- the TRV accepted the firmware image,
- the firmware was written successfully to flash,
- the TRV successfully rebooted,
- the patched firmware is operating correctly,
- either firmware patch is active at runtime,
- battery consumption has improved.

For this reason the server deliberately treats firmware installation status as
unknown after an HTTP transfer.

The device must be checked separately after the OTA request.

---

## Post-update verification

After the firmware transfer, allow the Shelly TRV time to process the update
and reboot.

The device should then become reachable again.

Verify that the reported firmware is:

```text
Device:  SHTRV-01
Version: 2.2.4
Build:   20240619-130912/v2.2.4@ee290818
```

Also verify normal device operation, including:

- Wi-Fi connectivity
- cloud connectivity, if enabled
- temperature measurement
- thermostat operation
- calibration state
- valve movement

Because the patch does not modify the firmware version string, `/status`
cannot by itself prove that the patched image is installed.

Runtime testing is therefore performed separately.

For this project, runtime validation includes:

- debug-log analysis for beacon-skip recovery behavior,
- packet capture for periodic mDNS activity,
- longer-term monitoring with the battery logger.

## Windows Firewall

On Windows, the firewall may ask whether Python is allowed to accept incoming
network connections.

The Shelly TRV must be able to establish an HTTP connection to the computer
running `ota_server.py`.

If the firmware URL works on the computer itself but the TRV cannot retrieve
the firmware, check:

- Windows Firewall permissions
- whether the computer and TRV can communicate on the local network
- whether the detected local IPv4 address is correct
- whether the selected TCP port is reachable
- whether another security product blocks incoming connections

A useful connectivity test is to request the firmware URL from another device
on the same local network.

---

## macOS

On macOS, TCP port 80 normally requires elevated privileges.

The tested start command is:

```bash
sudo python3 ota_server.py
```

The user may be asked for the local macOS account password.

The password is handled by `sudo` and is not processed by `ota_server.py`.

If macOS asks whether Python is allowed to accept incoming network
connections, access must be permitted for the TRV to retrieve the firmware.

If the server starts successfully and prints a local firmware URL, that URL
can be tested with:

```bash
curl -v -o /dev/null "http://<COMPUTER-IP>/SHTRV-01_2.2.4_beacon_mdns_patch.gbl"
```

## Troubleshooting

### Firmware file is missing

Confirm that the patcher has already been run successfully.

The OTA server expects:

```text
target/SHTRV-01_2.2.4_beacon_mdns_patch.gbl
```

The server no longer accepts an arbitrary firmware path on the command line.

### Firmware validation fails

Confirm that the file was generated by the current combined-patch version of:

```text
patch_firmware_v.1.0.py
```

The expected patched SHA-256 is:

```text
7adbb31d6b7faa8b9290d7b3436af45d42af9c3602a7195cafab774ded84ac61
```

Expected CRC32:

```text
0xBAEB8265
```

Expected size:

```text
1,106,384 bytes
```

Do not bypass firmware validation to serve an unknown image.

### Old beacon-only patched firmware is rejected

Earlier development versions of the project generated a firmware image with a
different hash and CRC32.

The current OTA server intentionally accepts only the current combined
Patch A+B image.

An older patched firmware file must not be renamed in an attempt to bypass
validation.

Generate a new combined patched image from the exact supported original
firmware using the current patcher.

### Port 80 cannot be used

The server automatically attempts port 8000 if port 80 cannot be used.

Use the exact firmware and OTA URLs printed by the program.

On macOS or Linux, starting the server with:

```bash
sudo python3 ota_server.py
```

normally allows use of port 80 if the port is otherwise available.

### Firmware URL cannot be reached

Check:

- the detected local IPv4 address,
- local firewall configuration,
- network connectivity between the TRV and computer,
- the selected TCP port,
- whether the OTA server is still running.

The TRV and computer must be able to communicate with each other.

### Browser or curl download works but OTA does not

A successful HTTP download confirms only that the OTA server is reachable and
can serve the firmware.

Check:

- the target TRV IP address,
- the exact OTA URL,
- whether the TRV can reach the computer,
- whether the OTA server remains running,
- the server console for incoming requests or errors.

### Transfer completes but the TRV does not return

Do not assume that HTTP completion means installation succeeded.

Allow time for firmware processing and reboot.

Then check whether the device becomes reachable again.

If it does not, further device-level troubleshooting is required.

### Wrong local IP address is detected

Automatic address detection works for the tested network configuration, but
systems with multiple active interfaces or VPN software may have more than one
possible local address.

The address used by the OTA server must be reachable from the Shelly TRV.

---

## Security

The OTA server is intended only for temporary use on a trusted local network.

It:

- does not provide authentication,
- does not provide TLS,
- should not be exposed directly to the public Internet,
- should be stopped after the OTA operation is complete.

The server serves only the validated patched firmware path and does not provide
general file-system access.

The server does not upload the firmware to an external service.

---

## Stopping the server

After the OTA operation and device verification are complete, stop the server
with:

```text
Ctrl+C
```

The server does not need to remain running after the firmware update.
