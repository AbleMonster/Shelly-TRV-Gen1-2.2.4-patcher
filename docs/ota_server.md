# OTA Server

This document describes the local OTA firmware server included with the Shelly TRV Gen1 2.2.4 Firmware Patcher project.

The server is implemented in:

```text
ota_server.py
```

It is intended specifically for transferring the qualified experimental B2.2 firmware generated by:

```text
patch_firmware_v2.0.py
```

to a Shelly TRV Gen1 (`SHTRV-01`) on the local network.

The OTA server is not a general-purpose firmware server, HTTP file server, firmware downloader, or device-management service.

---

## Purpose

The Shelly TRV Gen1 can retrieve firmware through its OTA HTTP interface.

`ota_server.py` provides a small local HTTP/1.1 server that:

1. locates the expected B2.2 GBL in `target/`,
2. validates the firmware before serving it,
3. determines a local IPv4 address,
4. requires TCP port 80,
5. serves only the expected B2.2 firmware path,
6. supports HTTP byte-range requests,
7. displays transfer progress,
8. prints the firmware URL,
9. prints an OTA URL template for the Shelly TRV.

The OTA server does **not** modify firmware.

Firmware reconstruction is performed separately by:

```text
patch_firmware_v2.0.py
```

The OTA server also does **not** automatically initiate an OTA update.

The user must explicitly request the Shelly OTA endpoint using the URL printed by the server or an equivalent request.

## Requirements

The OTA server requires:

- Python 3,
- the exact B2.2 GBL generated by `patch_firmware_v2.0.py`,
- a computer on a network reachable by the Shelly TRV,
- network connectivity from the TRV to TCP port 80 on that computer.

No third-party Python packages are required.

The server uses only the Python standard library.

## Firmware validation

Before opening the HTTP server, `ota_server.py` validates the B2.2 GBL.

Validation includes:

- file existence,
- regular-file check,
- exact file size,
- exact SHA-256,
- stored END CRC32,
- independently calculated END CRC32,
- comparison against the expected B2.2 END CRC32.

The server starts only if all checks succeed.

The expected values are:

```text
Filename:
SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl

Size:
1,126,156 bytes

SHA-256:
912983973a5467241397b9dd967ee0039440c7d77780a2a97ee494b1a507860c

END CRC32:
0x52A97051
```

If any validation check fails, the HTTP server is not started.

Firmware validation must not be bypassed to serve an unknown or modified image.

## Starting the server

First generate B2.2:

```bash
python3 patch_firmware_v2.0.py
```

The required OTA output is:

```text
target/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

Then start the OTA server.

On macOS and Linux, binding to TCP port 80 normally requires elevated privileges:

```bash
sudo python3 ota_server.py
```

No firmware argument is required.

The server automatically resolves:

```text
target/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

relative to its own location.

---

## TCP port 80 requirement

The current server intentionally uses:

```text
TCP port 80
```

only.

There is no automatic fallback to TCP port 8000.

This reflects the observed Shelly TRV Gen1 OTA behavior in this project.

During earlier testing, a Python HTTP server on port 8000 could be reachable from another client and the TRV could accept an `/ota` request, while the expected firmware HTTP retrieval from the TRV did not follow successfully.

Using TCP port 80 resulted in the expected firmware request.

For this project, the supported local OTA workflow is therefore:

```text
Shelly TRV Gen1 OTA
→ HTTP
→ TCP port 80
```

If port 80 is already in use, the current OTA server fails closed instead of silently selecting another port.

## Network detection

The server attempts to determine a usable local IPv4 address automatically.

The detected address is used both for:

- binding the HTTP server,
- constructing the firmware URL printed to the console.

Example:

```text
Local IPv4 : 192.168.178.232
```

The actual address depends on the host and network.

The Shelly TRV must be able to reach that address.

### Multiple interfaces and VPNs

Systems with:

- VPN software,
- multiple network adapters,
- multiple private IPv4 networks,
- unusual routing,

may expose more than one usable private address.

The automatically selected address must therefore be checked before starting an OTA request.

If the displayed address is reachable only through a VPN or another interface that the TRV cannot access, the OTA operation will not work even though the server itself started successfully.

## Starting the Shelly OTA update

The Shelly TRV OTA endpoint accepts a firmware URL.

General form:

```text
http://<SHELLY-TRV-IP>/ota?url=http://<COMPUTER-IP>/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

Example:

```bash
curl "http://192.168.178.226/ota?url=http://192.168.178.232/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl"
```

Use the actual TRV IP address and the actual local IPv4 address printed by the OTA server.

Keep `ota_server.py` running until the firmware transfer has completed.

Do not intentionally interrupt power to the TRV while firmware installation is in progress.

## Expected OTA response

When an OTA request is accepted, the Shelly TRV can return a response similar to:

```json
{
  "status": "updating",
  "has_update": true,
  "new_version": "20240619-130912/v2.2.4@ee290818",
  "old_version": "<previous firmware build>"
}
```

The exact previous firmware version depends on the device being updated.

B2.2 deliberately retains the native Shelly firmware identity:

```text
20240619-130912/v2.2.4@ee290818
```

Therefore the version reported by the TRV does **not** distinguish B2.2 from unmodified Stock 2.2.4.

## HTTP implementation

The server uses:

```text
HTTP/1.1
```

and advertises:

```text
Accept-Ranges: bytes
```

The HTTP server identity is:

```text
ShellyTRVOTA/2.0
```

A normal request receives:

```text
HTTP/1.1 200 OK
```

A valid byte-range request receives:

```text
HTTP/1.1 206 Partial Content
```

The implementation supports:

```text
Range: bytes=0-
Range: bytes=<start>-<end>
Range: bytes=<start>-
Range: bytes=-<length>
```

Invalid or unsatisfiable ranges are rejected.

Multiple byte ranges in one request are not supported.

## Served paths

The OTA server is deliberately restrictive.

It serves only:

```text
/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

It does not provide:

- directory listings,
- general access to `target/`,
- arbitrary local-file access,
- a firmware upload endpoint,
- a generic download service.

Requests for unrelated paths are rejected.

- number of transferred bytes,
- transfer percentage,
- progress bar,

## Meaning of transfer completion

A completed HTTP transfer means only that the requested firmware bytes were successfully written to the HTTP connection.

It does **not** prove that:

- the TRV accepted the firmware container,
- firmware was successfully written to flash,
- the device rebooted successfully,
- B2.2 is operating correctly after boot,
- long-term stability is established,
- battery consumption has improved,
- the historical battery-drain root cause has been identified.

The server therefore deliberately reports firmware-installation status as unknown after the HTTP transfer.

Device behavior must be checked separately.

## Windows Firewall

On Windows, the firewall may ask whether Python is allowed to accept incoming connections.

The Shelly TRV must be able to establish an HTTP connection to TCP port 80 on the computer running `ota_server.py`.

If the server starts but the TRV cannot retrieve firmware, check:

- Windows Firewall permissions,
- local network connectivity,
- the detected local IPv4 address,
- whether TCP port 80 is reachable,
- whether security software blocks incoming connections.

---

## macOS

On macOS, binding TCP port 80 normally requires elevated privileges.

Use:

```bash
sudo python3 ota_server.py
```

The local account password is handled by `sudo` and is not processed by the OTA server.

If macOS asks whether Python should be allowed to accept incoming network connections, access must be allowed for the TRV to retrieve firmware.

## Troubleshooting

### Firmware file is missing

The server expects:

```text
target/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

Run:

```bash
python3 patch_firmware_v2.0.py
```

first if B2.2 has not yet been generated.

---

### Firmware validation fails

Confirm:

```text
Filename:
SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl

Size:
1,126,156 bytes

SHA-256:
912983973a5467241397b9dd967ee0039440c7d77780a2a97ee494b1a507860c

END CRC32:
0x52A97051
```

Do not rename an unrelated or historical patched image in an attempt to bypass validation.

Do not disable the validation checks.

---

### Stock firmware is rejected

This is expected.

`ota_server.py` serves the generated B2.2 GBL, not the Stock 2.2.4 input.

The Stock firmware belongs at:

```text
target/SHTRV-01_build_2.2.4.gbl
```

for use by:

```text
patch_firmware_v2.0.py
```

It is not the image served by the B2.2 OTA server.

---

### Historical v1.0 patched firmware is rejected

This is expected.

Earlier project versions generated different experimental firmware identities, including the historical Beacon Recovery + periodic mDNS patch.

The current OTA server accepts only the exact B2.2 GBL.

Historical artifacts must not be renamed to the B2.2 filename.

---

### Port 80 cannot be used

The current server does **not** fall back to port 8000.

On macOS or Linux, first ensure the server is started with:

```bash
sudo python3 ota_server.py
```

If port 80 is still unavailable, determine which process currently owns it before continuing.

Do not silently substitute port 8000 for the supported TRV Gen1 OTA workflow.

---

### Wrong local IP address is detected

This is particularly relevant on systems using VPN software or multiple network interfaces.

Confirm that the IPv4 address printed by the server is reachable from the Shelly TRV.

The fact that the address is valid and private does not guarantee that it belongs to the LAN interface used by the TRV.

---

### Browser or curl download works but OTA does not

A successful browser or `curl` download proves only that an HTTP client can reach the OTA server.

Check:

- target TRV IP address,
- exact OTA URL,
- server IPv4 address,
- network path from the TRV to the server,
- TCP port 80,
- server console for incoming requests,
- whether the server remains running.

---

### Transfer completes but the TRV does not return

Do not interpret HTTP completion as proof of successful firmware installation.

Allow time for processing and reboot.

Then check whether the TRV becomes reachable again.

If it does not, device-level recovery or troubleshooting may be required.

---

## Security

The OTA server is intended only for temporary use on a trusted local network.

It:

- provides no authentication,
- provides no TLS,
- should not be exposed directly to the public Internet,
- should be stopped when no longer needed.

The server exposes only the exact validated firmware path.

It does not provide general file-system access.

The firmware is not uploaded to an external service by the OTA server.

---

## Stopping the server

Stop the server with:

```text
Ctrl+C
```

The server does not need to remain running after the OTA operation has completed.

## Scope

`ota_server.py` is intentionally specific to this project.

It serves the exact experimental B2.2 Shelly TRV Gen1 2.2.4 firmware generated and validated by:

```text
patch_firmware_v2.0.py
```

It is not intended to be:

- a general Shelly OTA server,
- a general firmware web server,
- a firmware downloader,
- a firmware patcher,
- a remote management service.

The patcher reconstruction and qualification details are documented separately.

The OTA server is only the validated local transfer mechanism.

Most importantly:

```text
exact B2.2 reconstruction
!=
successful OTA installation
!=
hardware qualification
!=
long-term battery improvement
!=
historical battery-drain root cause proven
```

These boundaries must remain explicit throughout the project documentation.
