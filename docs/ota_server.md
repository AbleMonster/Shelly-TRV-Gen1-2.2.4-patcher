# OTA Server – Shelly TRV Gen1 B2.2 Beta

This document describes the local OTA firmware server supplied with the **Shelly TRV Gen1 (SHTRV-01) Firmware Patcher v2.0**.

The server makes the qualified **B2.2 Beta** firmware available to a Shelly TRV over the local network using HTTP.

**Last updated:** November 9, 2026
**OTA server:** 2.0, revision 1
**Firmware:** B2.2 Beta
**Required port:** TCP 80

> **Important**
>
> The OTA server does not modify firmware or initiate updates automatically.
>
> It validates and serves one exact B2.2 GBL file. The user must explicitly initiate installation through the Shelly TRV OTA endpoint.
>
> An HTTP transfer does not prove successful firmware installation or device operation.

## 1. Purpose and Architecture

The OTA server is implemented in:

```text
ota_server.py
```

It works together with:

```text
patch_firmware_v2.0.py
```

The two tools have different responsibilities.

| Component | Responsibility |
|---|---|
| Firmware patcher | Reconstructs and verifies B2.2 from the supported Stock firmware |
| OTA server | Validates and transfers the generated B2.2 GBL |
| Shelly TRV | Requests, processes and installs the firmware |

### OTA workflow

```text
Original Stock 2.2.4 GBL
            |
            v
patch_firmware_v2.0.py
            |
            v
Verified B2.2 OTA GBL
            |
            v
ota_server.py
            |
            v
HTTP transfer over TCP port 80
            |
            v
Shelly TRV OTA interface
            |
            v
Device-side validation and installation
            |
            v
Device reboot and functional verification
```

The server is not a general-purpose HTTP file server, firmware downloader, firmware editor or remote device-management service.

## 2. Server Version

The current implementation uses:

```text
VERSION  = 2.0
REVISION = 1
```

HTTP server identity:

```text
ShellyTRVOTA/2.0
```

The patcher and OTA server are versioned independently.

To display the server version:

```bash
python3 ota_server.py --version
```

Expected output:

```text
ota_server.py 2.0 revision 1
```

A syntax check can be performed without starting the server:

```bash
python3 -m py_compile ota_server.py
```

Successful compilation normally produces no output.

## 3. Requirements

The server requires:

- Python 3
- The exact B2.2 GBL generated by the patcher
- A Windows, macOS or Linux computer
- Network connectivity from the Shelly TRV to the computer
- Available TCP port 80
- A trusted local network

No third-party Python packages are required.

The server uses the Python standard library.

### Local directory structure

The patcher and server use the repository's `target/` directory.

After successful reconstruction:

```text
target/
├── .gitkeep
├── SHTRV-01_build_2.2.4.gbl
├── SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.bin
└── SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

The OTA server serves only:

```text
target/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

The original Stock GBL and standalone application BIN are not served.

Firmware files must remain local and must not be committed to the public repository.

## 4. Supported Firmware Identity

The OTA server accepts only the exact qualified B2.2 GBL.

| Property | Expected value |
|---|---|
| Device | Shelly TRV Gen1 / SHTRV-01 |
| Base firmware | Stock 2.2.4 |
| Firmware classification | B2.2 Beta |
| Filename | `SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl` |
| File size | 1,126,156 bytes |
| END CRC32 | `0x52A97051` |
| Whole-file CRC32 residue | `0x2144DF1C` |

**Expected SHA-256:**

```text
912983973a5467241397b9dd967ee0039440c7d77780a2a97ee494b1a507860c
```

The `EXPERIMENTAL` filename is intentionally retained to preserve the existing qualified artifact identity and server workflow.

The firmware is classified as **Beta** for public testing.

### Related application identity

The patcher also generates:

```text
SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.bin
```

Expected size: **1,069,320 bytes**

Expected SHA-256:

```text
7ee593265c76abd8cd628a81133d4b1310c1ae24c9ebe2ca3f2c2948acfc64f9
```

Expected CRC32:

```text
42657D97
```

The OTA server does not serve this standalone application binary.

## 5. Firmware Validation

Before opening the HTTP server, `ota_server.py` independently validates the generated GBL.

The validation includes:

1. Checking file existence.
2. Checking that the expected path refers to a regular file.
3. Verifying the exact file size.
4. Calculating and comparing SHA-256.
5. Reading the stored GBL END CRC32.
6. Independently calculating the END CRC32.
7. Comparing the result with the expected B2.2 value.

The server starts only when all checks succeed.

### Fail-closed behavior

If the firmware does not match the expected identity, the server refuses to start.

It must not serve:

- The original Stock firmware
- Historical v1.0 patched firmware
- A modified B2.2 image
- A truncated or corrupted GBL
- An unknown firmware renamed to the expected filename

Validation checks must not be disabled to force an unsupported firmware transfer.

The qualified B2.2 container also has a known whole-file CRC32 residue, but the server does not require a separate residue check because it validates exact size, SHA-256 and the GBL END CRC32.

## 6. Starting the OTA Server

First generate the B2.2 firmware using the patcher.

### Windows

```powershell
py patch_firmware_v2.0.py
```

Start the server:

```powershell
py ota_server.py
```

Windows Firewall may request permission for incoming connections.

Allow the required connection only on the appropriate trusted local network.

If port 80 cannot be bound, check local permissions and whether another application is already using the port.

### macOS / Linux

Generate the firmware:

```bash
python3 patch_firmware_v2.0.py
```

Start the server:

```bash
sudo python3 ota_server.py
```

Binding to TCP port 80 normally requires elevated privileges on these systems.

No firmware filename needs to be supplied as an argument.

The server automatically locates the expected B2.2 GBL relative to its own installation directory.

## 7. TCP Port 80

The current server uses:

```text
TCP port 80
```

There is no automatic fallback to port 8000.

This restriction reflects earlier physical Shelly TRV Gen1 OTA testing.

During those experiments, an HTTP server on port 8000 could be reached by other HTTP clients, while the expected TRV firmware retrieval did not complete as required.

Using port 80 resulted in the expected firmware request.

Therefore, the supported workflow for this project uses port 80.

If the port is unavailable, the current server does not silently select another port.

The port conflict must be resolved before continuing.

## 8. Network Detection

The server attempts to determine a usable local IPv4 address automatically.

This address is used for binding the HTTP server and constructing the firmware URL displayed in the console.

Example:

```text
Local IPv4 : 192.168.178.232
```

The actual address depends on the host system and network configuration.

### Multiple interfaces and VPNs

Computers may have multiple IPv4 addresses due to:

- Ethernet and Wi-Fi interfaces
- VPN software
- Multiple private networks
- Virtual network adapters
- Unusual routing configurations

The selected address must be reachable from the Shelly TRV.

A valid private IPv4 address is not necessarily the correct address for the TRV's local network.

Always verify the displayed address before initiating an OTA update.

## 9. Firmware URL

The server exposes the B2.2 GBL under one fixed HTTP path:

```text
/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

For a computer using:

```text
192.168.178.232
```

the corresponding firmware URL is:

```text
http://192.168.178.232/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

The server prints its actual URL after successful startup.

Do not replace the local network address with `localhost` or `127.0.0.1` when instructing the TRV to download firmware.

Those addresses would refer to the requesting device itself.

## 10. Initiating the OTA Update

The Shelly TRV Gen1 exposes an HTTP OTA endpoint that accepts a firmware URL.

General request format:

```text
http://<TRV-IP>/ota?url=http://<COMPUTER-IP>/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

Example:

```bash
curl "http://192.168.178.226/ota?url=http://192.168.178.232/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl"
```

Replace both example addresses with the actual addresses of the TRV and OTA-server computer.

The same request can be entered in a browser.

### Expected response

The TRV may respond with information similar to:

```json
{
  "status": "updating",
  "has_update": true
}
```

Depending on the device state, additional firmware-version fields may be present.

A response indicating `updating` means the request was accepted.

**It does not establish that the firmware has already been downloaded, written to flash or successfully started.**

Keep the OTA server running throughout the transfer.

## 11. HTTP/1.1 Implementation

The OTA server implements:

```text
HTTP/1.1
```

It advertises:

```text
Accept-Ranges: bytes
```

The server supports full-file and single-range requests.

### Full-file request

A normal request receives:

```text
HTTP/1.1 200 OK
```

The response contains the requested firmware data.

### Byte-range request

A valid Range request receives:

```text
HTTP/1.1 206 Partial Content
```

Supported range forms include:

```http
Range: bytes=0-
Range: bytes=<start>-<end>
Range: bytes=<start>-
Range: bytes=-<length>
```

This allows a client to request all or a selected part of the firmware image.

Invalid or unsatisfiable ranges are rejected.

Requests containing multiple byte ranges are not supported.

### Restricted HTTP paths

The server exposes only:

```text
/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

It does not provide directory listings, general access to `target/`, arbitrary file access, firmware uploads or a generic download service.

Requests for unrelated paths are rejected.

## 12. Transfer Monitoring

During firmware transfer, the server provides console information including:

- Requesting client
- Requested byte range
- HTTP response status
- Requested data size
- Number of transmitted bytes
- Transfer progress and percentage
- Transfer rate
- Transfer duration
- Average transfer rate
- Completed or interrupted transfer status

For byte-range requests, the server also reports the transfer position relative to the complete firmware image.

### Meaning of a completed transfer

A completed transfer establishes that the server transmitted the requested bytes through the HTTP connection.

It does not prove that the TRV:

- Accepted the GBL container
- Successfully wrote the firmware to flash
- Completed the installation
- Rebooted correctly
- Started B2.2 successfully
- Is stable during subsequent operation

The server cannot determine the final device-side installation result from the HTTP transfer alone.

Device-level verification is required.

## 13. Post-Update Verification

After the firmware transfer, allow the TRV to complete processing and reboot.

Do not interrupt the device during installation.

Once it becomes reachable, verify:

- Wi-Fi connectivity
- Cloud connectivity, if enabled
- Temperature measurement
- Calibration state
- Thermostat operation
- Valve movement

### Firmware version reporting

B2.2 deliberately retains the original Shelly firmware identity:

```text
20240619-130912/v2.2.4@ee290818
```

Therefore, the `/status` endpoint continues to report native firmware version `2.2.4`.

This does not distinguish B2.2 from unmodified Stock firmware.

The generated firmware identity is established through the exact reconstruction and artifact hashes.

Successful installation additionally requires device-side operational verification.

## 15. Troubleshooting

### Firmware file missing

The OTA server requires:

```text
target/SHTRV-01_2.2.4_B2.2_EXPERIMENTAL.gbl
```

If it is missing, generate B2.2 using:

```bash
python3 patch_firmware_v2.0.py
```

### Firmware validation failed

Verify the expected filename, size and SHA-256.

Do not disable validation or rename another firmware image to bypass the checks.

### Original Stock firmware is rejected

This is expected.

The OTA server serves only the generated B2.2 GBL.

The original Stock image is an input to the patcher, not an accepted OTA-server artifact.

### Historical patched firmware is rejected

The historical v1.0 patcher produced a different firmware build.

The current OTA server intentionally rejects its output.

### Port 80 unavailable

On macOS or Linux, ensure that the server was started with:

```bash
sudo python3 ota_server.py
```

If the port is still unavailable, identify the conflicting process.

The supported configuration does not automatically switch to port 8000.

### Incorrect IP address

Verify that the IPv4 address printed by the server belongs to the network reachable by the TRV.

Pay particular attention to VPNs and computers with multiple interfaces.

### Browser download works but TRV OTA fails

A successful browser download proves that the browser can reach the server.

It does not prove that the TRV can reach the same address.

Verify the TRV IP, server IP, OTA URL, TCP port 80, firewall configuration and incoming requests in the OTA-server console.

### Transfer completes but the TRV does not return

An HTTP transfer does not guarantee successful firmware installation.

Allow the device to process the update.

If it does not become reachable, device-level recovery or troubleshooting may be required.

### TRV restarts unexpectedly after installation

Unexpected automatic restarts are a known B2.2 Beta issue under investigation.

Record the time, uptime, reboot counter and available diagnostic information.

Do not assume that a restart was caused by a Watchdog timeout without reset-cause evidence.

## 16. Security

The OTA server is intended only for temporary operation on a trusted local network.

It:

- Does not provide authentication
- Does not provide TLS encryption
- Must not be exposed directly to the public Internet
- Does not upload firmware to an external service
- Does not provide general filesystem access
- Should be stopped when no longer required

Because the server binds to a local network address, other clients with network access to that address may be able to request the validated firmware file.

Access should therefore be restricted to a trusted environment.

### Stop the server

After completing the OTA operation, stop the server using:

```text
Ctrl+C
```

The server does not need to continue running after installation.

## 17. Scope and Evidence Limits

The OTA server is a validated local firmware-transfer tool.

Its responsibilities end at providing the expected B2.2 firmware bytes over HTTP.

The following must remain separate:

```text
Exact firmware reconstruction
            !=
Successful HTTP transfer
            !=
Successful OTA installation
            !=
Verified physical operation
            !=
Long-term firmware stability
            !=
Battery-life improvement
            !=
Historical battery-drain root cause proven
```

A successful OTA-server operation does not establish higher-level firmware or device properties.

For installation instructions, see [User Guide](../USER_GUIDE.md).

For the firmware implementation, see [Technical Details](technical-details.md).

For current validation and physical testing, see [Testing](../tests/README.md).

## Conclusion

`ota_server.py` version 2.0 revision 1 provides a deliberately restricted local HTTP/1.1 OTA transfer mechanism for one exact qualified Shelly TRV Gen1 B2.2 firmware image.

It validates the firmware identity, serves the GBL over TCP port 80, supports byte-range requests and reports transfer progress.

The OTA server does not modify firmware, automatically start updates or determine device-side installation success.

**The current firmware classification is B2.2 Beta. Known firmware reliability issues are documented separately from OTA-server transport validation.**
