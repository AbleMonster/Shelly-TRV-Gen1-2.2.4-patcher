# OTA Server

This document describes the local OTA firmware server included with the
Shelly TRV Gen1 2.2.4 Firmware Patcher project.

The server is implemented in:

```text
ota_server.py
```

It is intended specifically for transferring the patched Shelly TRV 2.2.4
firmware generated by `patch_firmware.py` to a Shelly TRV (SHTRV-01) on the
local network.

It is not intended to be a general-purpose firmware or HTTP server.

## Purpose

The Shelly TRV can retrieve firmware through its OTA HTTP interface.

`ota_server.py` provides a small local HTTP/1.1 server that:

1. validates the patched firmware before serving it,
2. detects a suitable local IPv4 address,
3. selects an available HTTP port,
4. serves only the expected patched firmware,
5. supports HTTP Range requests,
6. displays firmware-transfer progress,
7. prints the firmware URL,
8. prints an OTA URL template for the Shelly TRV.

The server does **not** modify firmware.

Firmware modification is performed separately by:

```text
patch_firmware.py
```

The server also does **not** automatically initiate an OTA update on a device.

The user explicitly starts the OTA operation using the URL printed by the
server.

## Requirements

The OTA server requires:

- Python 3
- the patched GBL generated by `patch_firmware.py`
- a computer connected to the same local network as the Shelly TRV
- network connectivity between the TRV and the computer

No third-party Python packages are required.

The server uses only the Python standard library.

## Expected firmware

The OTA server intentionally accepts only the exact patched firmware produced
by this project.

Expected patched GBL size:

```text
1,106,384 bytes
```

Expected patched GBL CRC32:

```text
0x432F734F
```

Expected patched GBL SHA-256:

```text
ac7d85c8e9239bebd3b134c4b93fc838859c613e59f7690650097da984ea7222
```

If the supplied file does not match the expected patched firmware, the server
refuses to serve it.

This prevents accidentally selecting an unrelated or incorrectly generated
firmware image.

## Starting the server

After generating the patched firmware, start the OTA server with:

```text
python ota_server.py SHTRV-01_2.2.4_patch.gbl
```

A different path can be supplied if the patched firmware is stored elsewhere.

For example:

```text
python ota_server.py "C:\Firmware\SHTRV-01_2.2.4_patch.gbl"
```

Before opening the HTTP server, the program validates the supplied firmware.

Validation includes:

- file existence
- file size
- SHA-256
- stored GBL CRC32
- calculated GBL CRC32
- expected patched CRC32

The server starts only if validation succeeds.

## Network detection

The server attempts to determine a suitable local IPv4 address automatically.

The detected address is used for the HTTP server and for the firmware URL
printed to the console.

Example:

```text
Local IPv4 : 192.168.178.159
```

The actual address depends on the local network.

The Shelly TRV must be able to reach this address.

Systems with multiple network adapters, VPN connections or unusual routing
configurations may require additional attention if the automatically detected
address is not reachable from the TRV.

## Port selection

The server checks the preferred HTTP ports in this order:

```text
80
8000
```

If port 80 is available, it is used.

If port 80 cannot be used, the server attempts to use port 8000.

Example using port 80:

```text
http://192.168.178.159/SHTRV-01_2.2.4_patch.gbl
```

Example using port 8000:

```text
http://192.168.178.159:8000/SHTRV-01_2.2.4_patch.gbl
```

On some operating systems, port 80 may require additional permissions or may
already be used by another application.

## Firmware URL

The firmware is served under the fixed filename:

```text
SHTRV-01_2.2.4_patch.gbl
```

After startup, the server prints the complete firmware URL.

Example:

```text
http://192.168.178.159/SHTRV-01_2.2.4_patch.gbl
```

This URL can also be opened from another device on the same local network to
confirm that the server is reachable.

A successful browser download confirms that the HTTP server can serve the
firmware over the network.

It does not test the Shelly OTA process itself.

## Starting the Shelly OTA update

The server prints an OTA URL template in the following form:

```text
http://<SHELLY-TRV-IP>/ota?url=http://192.168.178.159/SHTRV-01_2.2.4_patch.gbl
```

Replace:

```text
<SHELLY-TRV-IP>
```

with the local IP address of the target Shelly TRV.

For example, if the TRV uses:

```text
192.168.178.88
```

the resulting OTA request is:

```text
http://192.168.178.88/ota?url=http://192.168.178.159/SHTRV-01_2.2.4_patch.gbl
```

Open this URL while `ota_server.py` is running.

The TRV then requests the firmware from the local OTA server.

Keep the server running until the firmware transfer has completed.

Do not intentionally interrupt power to the TRV while the firmware update is
in progress.

## HTTP implementation

The OTA server uses:

```text
HTTP/1.1
```

It supports both normal and byte-range firmware requests.

A normal request without a `Range` header receives:

```text
HTTP 200 OK
```

A valid byte-range request receives:

```text
HTTP 206 Partial Content
```

The server advertises:

```text
Accept-Ranges: bytes
```

## Range request support

Supported range forms include:

```text
Range: bytes=0-
Range: bytes=<start>-<end>
Range: bytes=<start>-
Range: bytes=-<length>
```

For example:

```text
Range: bytes=0-
```

requests the firmware beginning at byte zero.

This request form was observed during successful OTA transfer testing with a
physical Shelly TRV.

For valid range requests, the server returns the corresponding byte range and
a `Content-Range` response header.

Invalid or unsatisfiable ranges are rejected with:

```text
HTTP 416 Range Not Satisfiable
```

Multiple ranges in a single request are not supported.

## Served paths

The OTA server is deliberately restrictive.

It serves only the expected firmware path:

```text
/SHTRV-01_2.2.4_patch.gbl
```

It does not provide directory listings or expose arbitrary files from the
computer.

Requests for unrelated paths are rejected.

## Transfer progress

During a firmware transfer, the server displays progress information in the
console.

The displayed information can include:

- requesting client
- requested byte range
- HTTP response status
- number of bytes requested
- number of bytes transferred
- transfer percentage
- progress bar
- current transfer rate
- transfer duration
- average transfer rate
- completion or interruption status

This makes it possible to observe whether the TRV is actively retrieving the
firmware.

## Meaning of transfer completion

A completed HTTP transfer means that the server successfully wrote the
requested firmware data to the HTTP connection.

It does **not** prove that:

- the TRV accepted the firmware image,
- the firmware was written successfully to flash,
- the TRV successfully rebooted,
- the patched firmware is operating correctly.

For this reason the server deliberately reports firmware installation status
as unknown.

The device must be checked separately after the OTA request.

## Post-update verification

After the firmware transfer, allow the Shelly TRV time to process the update
and reboot.

The device should then become reachable again.

Verify that the reported firmware is:

```text
Device:  SHTRV-01
Version: 2.2.4
Build:   20240619-130912/v2.2.4@ee290818
```

Also verify normal device operation, including:

- Wi-Fi connectivity
- cloud connectivity, if enabled
- temperature measurement
- thermostat operation
- calibration state
- valve movement

For investigation of the beacon-skip behavior, runtime logs and device
statistics can additionally be inspected.

## Physical-device testing

The OTA server has been used successfully to transfer the patched firmware to
a physical Shelly TRV.

One documented OTA test used a TRV running the original firmware:

```text
Version: 2.1.3
Build:   20220202-080736/v2.1.3@d255ad74
```

The device was upgraded through the local OTA server to the patched firmware:

```text
Version: 2.2.4
Build:   20240619-130912/v2.2.4@ee290818
```

During that test:

- the OTA server validated the patched GBL,
- the server automatically selected the local IPv4 address,
- TCP port 80 was selected,
- the firmware was successfully transferred,
- the TRV accepted the firmware and rebooted,
- the device reported firmware 2.2.4 after reboot,
- Wi-Fi connectivity operated after the update,
- cloud connectivity operated after the update,
- thermostat calibration completed successfully,
- valve movement operated normally,
- normal RSSI-dependent beacon-skip selection was observed,
- the targeted recurring beacon-skip recovery sequence was not observed during
  the monitored post-update period.

These results demonstrate successful operation of the OTA workflow under the
tested conditions.

They do not establish long-term firmware stability or improved battery life.

## Windows Firewall

On Windows, the firewall may ask whether Python is allowed to accept incoming
network connections.

The Shelly TRV must be able to establish an HTTP connection to the computer
running `ota_server.py`.

If the firmware URL works on the computer itself but the TRV cannot retrieve
the firmware, check:

- Windows Firewall permissions
- whether the computer and TRV can communicate on the local network
- whether the detected local IPv4 address is correct
- whether the selected TCP port is reachable
- whether another security product blocks incoming connections

A useful connectivity test is to open the firmware URL from another device on
the same local network.

## Troubleshooting

### Firmware validation fails

Confirm that the file was generated by the current `patch_firmware.py`.

The expected patched SHA-256 is:

```text
ac7d85c8e9239bebd3b134c4b93fc838859c613e59f7690650097da984ea7222
```

Do not bypass firmware validation to serve an unknown image.

### Port 80 cannot be used

The server automatically attempts port 8000.

Use the exact firmware and OTA URLs printed by the program.

### Firmware URL cannot be reached

Check the detected local IPv4 address and firewall configuration.

The TRV and the computer must have network connectivity to each other.

### Browser download works but OTA does not

A successful browser download confirms only that the HTTP server is reachable.

Check:

- the target TRV IP address,
- the exact OTA URL,
- whether the TRV can reach the computer,
- whether the OTA server remains running,
- the server console for incoming requests or errors.

### Transfer completes but the TRV does not return

Do not assume that HTTP completion means installation succeeded.

Allow time for firmware processing and reboot.

Then check whether the device becomes reachable again.

If it does not, further device-level troubleshooting is required.

### Wrong local IP address is detected

Automatic address detection works for the tested network configuration but
systems with multiple active interfaces or VPN software may have more than one
possible local address.

The address used by the OTA server must be reachable from the Shelly TRV.

## Security

The OTA server is intended only for temporary use on a trusted local network.

It:

- does not provide authentication,
- does not provide TLS,
- should not be exposed directly to the public Internet,
- should be stopped after the OTA operation is complete.

The server serves only the validated patched firmware path and does not provide
general file-system access.

## Stopping the server

After the OTA operation and device verification are complete, stop the server
with:

```text
Ctrl+C
```

The server does not need to remain running after the firmware update.

## Scope

`ota_server.py` is intentionally specific to this project.

It is designed to serve the exact patched Shelly TRV 2.2.4 firmware generated
and validated by `patch_firmware.py`.

It is not intended to be:

- a general Shelly OTA server,
- a general firmware web server,
- a firmware downloader,
- a firmware patcher,
- a device-management service.

The firmware modification itself is documented in:

```text
docs/technical-details.md
```

The validation and physical-device testing are documented in:

```text
tests/README.md
```
